## SILENT pitfalls (run, wrong vs Python/JS) — the dangerous list

S1 `1 + "a"` → `"1a"` (concat, not error).
S2 `len("é")` → `2` bytes, not 1 char.
S3 `7 / 2` → `3` (truncates); `-7 / 2` → `-3` (Python floor `-4`).
S4 `0 - 7 % 3` → `-1` (Rust remainder; Python `2`).
S5 `1 && 2` → `1`, `0 || 5` → `1` (Bool 0/1, not operand).
S6 `print(true)` → `1` (not `True`).
S7 `sort(a)` returns copy; input unchanged.
S8 `push(a, v)` returns length, not array.
S9 `m[0]` → first key (not KeyError).
S10 `args()` excludes prog name (empty with no args).
S11 `read_line()` is `""` at EOF and for empty line (need `is_eof()`).
S12 `env("X")` missing → `""` (not None, indistinguishable from empty).
S13 struct/array/map params pass-by-value (caller unchanged).
S14 `fn main()` (no arrow) always exits 0, discards value.
S15 exit codes wrap 8-bit (`256`→`0`, `-1`→`255`).
S16 `format(a, b)` joins with spaces (not Python format).
S17 `spawn`/`run` argv-only, no shell/glob/pipe (silent no-expansion).

## Top 10 most confusing diagnostics

1. `with open(..)` / `elif` → `E-PARSE` "expected a `\"key\"` or `key` in
   map literal" (mentions maps for control-flow keywords).
2. `x == None` / `if True` (capitalized) → `E-PARSE` "expected field name";
   but `print(True)` → `E-UNDEFINED` "undefined variable `True`" (same word,
   different codes by position).
3. `f"hi {x}"` → `E-PARSE` "expected `)`" (no hint that f-strings do not exist).
4. `print("a", "b")` → `E-PARSE` "expected `)`" (no hint: 1 arg only, use `format`).
5. `a[1:2]` → `E-PARSE` "expected `]`" (no hint: use `slice(a, 1, 2)`).
6. `1 in [1,2]` → `E-PARSE` "expected `{`" (no hint: use `.contains()`).
7. `m.field` on maps → `E-TYPE` "field base: want struct, got map" (correct
   but Python users need `m["field"]` in fixes).
8. `1 == true` → `E-TYPE` "`==` operands: want i32, got bool" (names one side
   as expected; real rule is same-type-or-int/float-mix).
9. `set_env("", _)` → Rust panic, exit 101, no diagnostic (see bug above).
10. Unknown CLI flags: `run --sandbox` silently ignored (filtered as flag);
    `check --json` treated as filename (`E-IO-NOT-FOUND` for `"--json"`).
    Registry commands reject unknown flags (`unknown option`), but
    `run`/`check` do not — AI-supplied flags vanish silently.

## Docs vs behavior (behavior wins)

- Task note says AI tools use `klang check --json`, `klang run --sandbox`,
  `klang fmt`. Neither `--json` nor `--sandbox` exists in this tree
  (`grep --json/--sandbox src/main.rs`: only comments). `check --json f`
  tries to resolve package `"--json"`; `run --sandbox f` drops the flag and
  runs `f`. Actual: `klang check <file>` always prints JSON diagnostics (no
  flag); `klang run <file>` auto-relaxes relative `..` (no flag). Guide
  documents actual commands and warns against the flags. No MCP server
  exists (task note correct; `klang mcp` still serves stdio but AI tools use
  CLI per task).
- `src/stdlib/process.rs` comment says empty `set_env` names "allowed on
  Unix" — behavior panics (see bug). Guide avoids empty names.
- Otherwise `docs/reference.md`, `docs/limitations.md`, `SPEC.md` matched
  probed behavior (short-circuit, `len()` bytes, `slice` Unknown, file-guard
  modes, `i32`/`u8` boundaries, `void main` exit 0, 8-bit wrap, `Bool`
  prints 0/1 as `Int` at runtime since `Value` has no `Bool` variant).
